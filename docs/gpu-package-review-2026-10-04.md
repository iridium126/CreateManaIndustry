# GPU 包裹性能与正确性审查

审查日期：2026-10-04。源码基线：`c2d76ba`。按用户给定前提，Create 自由包裹的原版 CPU 单线程运动严格慢于本项目 GPU 运动；本报告评价 GPU 实现自身的正确性、吞吐和整条管线成本，不重新争论该比较。未修改生产代码。

## 结论

自由包裹创建时转为服务端轻量记录，GPU 负责自由运动，服务端负责物品及机器事务，这一分工成立。双缓冲 Jacobi、异步 fence 读回、精确生命周期 ACK、槽位延迟回收、局部暂停和机器事务一次消费，都有合理实现及回归覆盖。

仍存在两个真实 GPU 探针复现的正确性问题：高速交叉包裹漏碰撞、无环境接触的虚空包裹不回收。持续环境接触的服务端确认配额又限制了活动包裹吞吐，不能只用碰撞 kernel 的容量代表可持续物流容量。

## 发现

### 1. [P1] 动态 CCD 的终点索引遗漏交叉轨迹

位置：`src/main/resources/assets/createmanaindustry/shaders/particles/packages/dynamic_sweep.glsl:41`，候选过滤在第 61 行；`PackagePhysicsGpu.java:283` 从预测终点建索引。

查询区域只包括自己的扫掠 AABB，加上双方尺寸的 padding；索引只存对方的预测终点。随后相对运动 narrow phase 虽然正确，但对方终点在区域外时根本不会执行。`fast_sweep_cells.comp` 仅标记 fastCells，不把另一条扫掠轨迹加入候选链表，因此不能补救。

真实 GPU 复现：半尺寸均为 0.5，A 从 `(-5,10,0)` 沿 X 运动，B 从 `(0,10,-5)` 沿 Z 运动，初速度均为 200 格/秒，单步 50 ms。拖曳后位移均为 9.8；二者在步中相交。实际得到 A=`(4.8,9.9216,0)`、B=`(0,9.9216,4.8)`，速度仍各为 196，状态均为活动，完全没有碰撞响应。该探针使用生产世界碰撞和承载投影路径。

建议：使 broad phase 对双方扫掠保守，例如为扫掠占据建立候选索引，或另建高速体候选结构；不要直接恢复对所有查询的巨大体积扩张而引入大面积预算暂停。增加垂直交叉、斜交、同向追越和不同速度的成对 CCD 回归。

### 2. [P2] 无接触、无燃烧的虚空包裹无法回收

位置：`environment.comp:39`；`PackageLightGameplay.java:60,128`。

GPU 在没有水火/机器/传送门接触且未燃烧时直接返回，不产生环境样本。服务端的低于 `minBuildHeight-64` 消费判断只在机器/传送门的 `contact()` 中执行，普通姿态提交也没有对应回收判断。

真实 GPU 探针在已覆盖的空场景中，从中心 Y=-129 开始运行十步，得到 Y=-133.063339，仍活动，环境 journal 的 written=0、terminal=0。对于最低高度 -64 的世界，这已经在回收高度以下；GPU 没有任何可触发服务端回收的消息。之后即使因覆盖、区域或客户端离开而暂停，持久记录仍保留。

建议：在已接受的服务端姿态提交上执行低高度生命周期判断，或增加经服务端验证的 GPU 虚空事件。无需引入 CPU 运动。补充跨越回收高度及读档后回收的集成测试。

### 3. [P1] 环境确认吞吐仅能持续服务约 256 个逐步产样本的包裹

位置：`PackageAuthorityManager.java:386`、`PackageEnvironmentGpu.java:11,72`、`environment_state.glsl`。

持续燃烧、持续接触机器都会每个成功游戏步写一个环境样本。服务端每客户端每 tick 仅允许 256 个样本；超额整事件返回，没有本 tick 的剩余前缀处理。单体 journal 满 20 个未确认样本后，运动也暂停。

若服务器和模拟同为 r tick/s，则需求为 `N*r` 样本/秒，服务上限为 `256*r`：只有 N<=256 才可能持续逐步推进。20 tick/s 时为 5120 样本/秒；200 tick/s 时为 51200。多区域共享同一 Peer 配额，增加区域不能扩大上限。

客户端每成功帧最多捕获 16 个事件，每个最多 20 个样本。在 F FPS 下上限为 `320*F` 样本/秒；60 FPS 为 19200，5 FPS 为 1600。200 tick/s、60 FPS 的理论上限因此进一步降至约 96 个持续产样本包裹，5 FPS 降至约 8 个。这些是理想批次满载上限；重复发送、ACK 延迟及不满批次会使实际能力更低。

真实 GPU 探针验证了机制：512 个包裹持续接触机器、刻意不发送 ACK，21 步后 512/512 全部暂停，保留 10240 个样本，单次 capture 只输出 16 个事件、320 个样本。该探针不是联机吞吐实测；联机长期超载结论来自上述生产配额和到达率。

建议：以机器阻塞/拒绝、长时间燃烧和混合区域作为吞吐场景；压缩可安全重放的连续计时状态、减少无变化机器接触重试，或按资源预算调整批量确认能力。保留终止/库存事务的可靠 journal，不能靠丢样本解决。

### 4. [P2] 环境接触的固定 36 格距离门槛与历史批次不一致

位置：`PackageLightGameplay.java:103`、`PackageAuthorityManager.java:391-394`。

环境样本携带历史命中位置，服务端却把它与处理时最新的包裹记录位置比较，超过 36 格就撤销该包裹的租约。姿态提交允许按多步追赶计算位移额度，而该距离门槛不考虑样本步号、批次步数或事件/增量管线的不同延迟。

因此合法历史样本与新确认终点相隔超过 36 格时必被拒绝，例如高速包裹在高 tick rate、低 FPS 的批次内先接触机器、随后继续移动。旧接触块本身和命中 AABB 即使都合法，也无法通过该判断。此项通过代码路径确认，未做实际多人时序复现。

建议：对齐环境和姿态确认步号，为历史接触提供有界的对应基线/位移校验，保留身份、租约和真实方块校验。增加 ACK 延迟、200 tick/s 低帧率与高速长扫掠的交叉测试。

### 5. [P2] 自由包裹输入等待阻塞独立锁链域

位置：`PackageWorldRuntime.java:230-244`。

有自由包裹时，力源 worker、历史几何、moving 银行或 force 上传银行不可用都会直接 break 整个步进循环；锁链步进在这些检查之后。即使锁链轨道和自己的输入已经就绪，也会一起停住。两个 solver 资源独立，但调度并不独立。

这使自由场景加载/后台构建的延迟传播到锁链物流；继续增加 GPU 物理速度不能消除这一等待。此项通过控制流确认，未做游戏内延迟注入测试。

建议：分开记录两个域的可消费步与提交时钟，允许锁链继续推进，同时维护锁链事件及交接顺序。

### 6. [P2] 已有物理回归中的越界断言过时

位置：`scripts/particles/PackageGpuValidation.java:1770-1773`。

当前 `--physics-only` 和完整回归调用的 `dynamicPackageSweep()` 仍要求起点 ±4、速度 ±100 的成对运动暂停。拖曳后单体移动约 4.9 格，生产动态 CCD 当前允许每轴最多 32 格，实际正确停在 ±0.5、水平速度为零。运行因此报 `unbounded pair sweeps did not request local pause`。

这是测试断言过时，不是该迎面碰撞实现失败。但它会阻断物理专项和完整回归后续检查，历史文档中的全部通过不能作为当前 HEAD 的全部通过。

建议：将这组用例改为允许范围内的正常成对 CCD 验收，另以真正超过范围的位移检查局部暂停；同时加入发现 1 的交叉场景。

## 性能分析

### GPU 时间预算

仓库已有 `docs/benchmarks/package-index-2026-10-02/summary-5.csv`，以下为 linked、131072 个包裹、五轮各统计值的中位数。这是历史参考 fixture，不是本次对当前版本重新跑出的完整游戏性能。

| 场景 | GPU 单步 p50（ms） | GPU 单步 p95（ms） |
| --- | ---: | ---: |
| aligned_stack | 9.887 | 10.185 |
| staggered_stack | 9.983 | 10.313 |
| continuous_force | 10.191 | 10.459 |
| fast_vs_stationary | 9.284 | 9.808 |
| moving_platform | 8.794 | 9.097 |

按 p50 做容量预算，20 tick/s 的物理约占 0.176–0.204 GPU 秒/墙钟秒，尚有余量承担渲染；200 tick/s 的单步期限只有 5 ms，同一工作量约需 1.76–2.04 GPU 秒/墙钟秒，已超过实时预算。每帧允许补算四十步只是提交上限，不能增加 GPU 服务能力。这一推算不代替当前版本 200 tick/s 的实测。

生产承载路径每步默认四轮 Jacobi、四轮 cleanup，另有预测、CCD、环境和承载森林。空间索引通常重建十次（预测后一次、Jacobi 四次、承载前一次、cleanup 四次）；131072 时 pointer jumping 还有十七轮。优化应以这些 pass 的实测贡献和误差门槛为依据，不能随意删约束。

CPU submit p95 约 0.188–0.204 ms 只说明命令提交成本，不能代表 GPU 完成时间、整帧或服务端 tick；绘制准备阶段已有约 0.18–0.29 ms 的数字也未包含最终 mesh、片元及阴影成本。

### 常驻分配与扩展成本

在共享容量 C=131072 时，环境 headers+journal 单独申请 128 MiB。运行时每打开一个区域都创建容量 C 的 delta detector，基础 SSBO 为 `324*C + 1 MiB + 64 B`，约 41.5 MiB/区域；八区域约 332 MiB，尚不含通道读回、编码、物理/观察者/混合发布、粒子池和碰撞 atlas。

这些容量在活动数量很少时也会申请。该数值是代码定义的 buffer 申请量，不是驱动实际驻留显存；适合优先调查按需增长、共享输出银行和区域局部容量。已有 observer 基准也明确区分了申请量与驻留量。

服务端还有姿态解码、记录更新、空间索引、观察者复制、真实机器插入和 SavedData 保存成本。GPU 运动的优势成立，但这些外围成本不会随运动转到 GPU 自动消失。优先补充包含机器接触、确认积压和多个客户端的整帧/tick 测量。

## 按建议顺序的修复记录（2026-10-04）

上文保留修复前的审查证据。本次按上述顺序处理全部六项：

| 项目 | 处理 |
| --- | --- |
| 1：交叉 CCD | 高速路径按 cell 记录实际正负方向位移，扩展端点候选查询；同时覆盖慢速邻居的尺寸及位移，保留局部查询/候选预算。新增纵向、横向、两个方向、不同速度和两种支撑模式的真实 GPU 夹具。 |
| 2：虚空生命周期 | 创建/重新登记与已确认姿态更新加入虚空回收队列；有界消费当前精确记录，不依赖环境事件或 CPU 物理。GameTest 验证初始虚空记录、普通姿态越界与不能重复消费。 |
| 3：环境吞吐 | 单次捕获 16→512，环境 ACK 每帧独立处理最多 512 条；服务端环境消息独立预算，4096 条/32768 记录并受累计工作时间约束，超额确认已完成前缀。未发送的连续相同接触可合并，保留持续步数；已捕获记录保持不可变，ACK 逐步重放后缀。GPU 夹具覆盖 512 体、5 FPS、20/200 tick/s、延迟一帧 ACK；服务端验证合并后的逐步伤害。 |
| 4：历史接触 | 根据接触步与最新确认姿态步之间的历史跨度，使用相同的每轴扫掠预算验证可达性；保留身份、租约、时间窗口及实际方块校验。单元测试覆盖超过 36 格的合法历史接触和不可达/过期记录。 |
| 5：域调度 | 自由和锁链各用独立时钟提交；自由输入未就绪不会打断锁链推进。普通、光照和 Iris 路径使用各自插值；新增双时钟及不同插值的 GPU 姿态验证。 |
| 6：旧测试 | 将有界 ±100 blocks/s 对撞改为正确响应断言，另外用 ±1000 验证超限暂停。完整套件同时修正旧速度量化、观察者 80 字节布局及异步 view 背压夹具；GPU 绘制类由渲染入口接收 view scale，避免独立夹具初始化游戏注册表。 |

环境持续步数复用原 48 字节样本的尾部字段，权威协议升级为 `gpu-packages-13`；服务端与权威客户端必须同时升级。观察协议仍为 `gpu-package-observers-5`。新增局部 CCD 位移表在最大容量时占 4 MiB，比原标记表增加 3.5 MiB；环境捕获及读回环合计增加约 2.42 MiB。仍保留背压暂停，不能将扩大后的预算视作无限吞吐保证。

131072 个错层、持续驱动包裹的同环境对照：修复后三轮 GPU p50 为 10.966–12.793 ms，p95 为 13.386–16.034 ms；修复前 p50 为 13.861–14.132 ms，p95 为 15.983–17.214 ms。两组均零包裹重叠、零地形穿透、零回退、131036 体活动，三轮质量通过。p95 区间重叠，未观察到新增退化；不能据此声称加速，也不能与 10 月 1 日较低的历史计时直接比较。计时只覆盖推力探针及物理，不含绘制、网络和整帧。原始 CSV 见[本次验证摘要](benchmarks/package-review-fixes-2026-10-04/tests.json)。
