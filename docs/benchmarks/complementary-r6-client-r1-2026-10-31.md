# Complementary R6 客户端第一轮分析

本轮最重要的结论是：**低可见慢窗再次复现，但主要差距位于 `scene.compute` 之外；当前 MODEL 更新和主视角绘制不能解释它。优先补齐阴影与光影阶段归因，再决定优化路径。** 这是同一生产客户端进程的观察数据，不是优化前后 A/B，也不足以判断稳定收益。

- RTX 4070 Laptop、驱动 581.15、2560×1506、120 FPS 上限、VSync 关闭，均为 production-opengl，进程 6864。
- 光影均为 ComplementaryUnbound_r5.9.3；源码摘要 `da43d77bf336`，402 项选项摘要 `2f845d3b8761`。四份实际选项值、宏、附件和深度格式一致，引擎源码摘要一致。
- 同帧阶段记录与主帧匹配，无重复阶段行、无已知代次冲突、无缺失 census。每帧 MODEL 输入均为 65,527；不是通过清空模拟池取得零可见量。

## 低可见慢窗：已测更新不是主要差距

|GPU 范围 p50|低可见|近零可见|高可见|密集窗口|
|---|---:|---:|---:|---:|
|scene.compute|3.668|3.287|3.291|4.120|
|MODEL 更新|2.024|1.974|2.088|2.017|
|普通更新|0.074|0.073|0.075|0.076|
|输入准备|0.806|0.622|0.588|0.571|
|身体主视角绘制|0.051|0.009|2.974|3.146|
|透明／ghost 主视角绘制|0.036|0.002|1.721|1.864|
|羽毛绘制|0.074|0.035|0.069|0.077|

单位均为 ms。表中范围存在父子关系，不能把各项中位数相加构造整帧耗时。

低可见与近零窗口的主帧 GPU p50 相差约 6.70 ms，但 MODEL 更新仅相差约 0.05 ms。进一步对每帧匹配主帧 GPU 与其内部 `scene.compute`，先逐帧相减，再统计分位数：

- 低可见：compute 之外的 GPU 时间 p50 为 **15.564 ms**。
- 近零可见：该值为 **9.290 ms**。
- 逐帧余量分布的 p50 仍相差 **6.274 ms**。

这个余量包括所有其他绘制与等待，不能全部归给光影包，更不能全部归给云层。它说明当前继续单独追逐邻居查询，很难解释低可见慢窗。

核对代码发现两个关键诊断边界：

1. `sky.pack-stage.*` 包围的是 **Iris `CompositeRenderer.renderAll()` 的完整调用**。数字索引没有实际阶段／程序名映射；它不是“项目天空效果独占耗时”，不应据此把约 1–2 ms 全部算作云层。
2. `CMIPackEntityMergeHook` 已有 `SHADOW_TIMING`，但没有 observer label，本轮阶段 CSV 没有 MODEL 阴影范围及其提交数量。主相机只看见 258 个成员，不代表阴影相机也只处理 258 个。

此外，合并绘制的父级 `MERGE_TIMER` 也没有带标签导出。现有 body／ghost 只是子范围，不能覆盖它们之间的绑定、准备及等待。后续应同时导出合并绘制父范围，避免把本项目尚未覆盖的开销误归给光影包。

**阴影准备／绘制、阴影视锥提交量、其余世界渲染和光影阶段，是下一步应补齐的范围；目前还不能断定哪一项是根因。** 相机和完整场景初态没有写入当前窗口元数据，四窗攻击阶段也不同，不能将窗间差值直接当成单因素因果结果。

## 密集窗口：导航尾部需要独立关注

密集窗口中：

- Dome 接触 GPU p50/p95：**0.452 / 0.692 ms**。
- 导航 GPU p50/p95：**0.357 / 1.459 ms**。
- scene.compute p50/p95：**4.120 / 5.284 ms**。
- 身体、ghost 绘制 p95：**4.408 / 2.849 ms**。

按 CPU 攻击契约分组后，Dome assemble 的 856 帧中，导航 p50 约 **0.974 ms**，接触约 **0.391 ms**；Dome locked 的 716 帧中，导航约 **0.325 ms**，接触约 **0.569 ms**。这是一种阶段相关性，不是逐成员 GPU 阶段的完整复原，但已经说明不能把密集场景的全部计算尾部归为接触查询。

输入准备另有显著成本：四窗 p50 约 **0.57–0.81 ms**，p95 为 **1.17–1.64 ms**。该范围同时包含状态准备／复制、动画分配器、调度与计数器重置、伤害准备和原网格构建。它必须进一步拆分，不能全记为网格查询。此前连续网格未过完整链门槛，因此这里应先测各子项，再决定是否重做索引准备。

对控制流中互不嵌套、位于 scene.compute 内的 update 子范围逐帧求和后，未覆盖余量 p50 为 0.162–0.223 ms，主要计算范围的覆盖已较完整。这里的求和使用同帧兄弟范围，不是相加各段中位数。

## 四份快照与两条连续输入

四份 schema-2 快照完整，均有 65,527 个风暴成员，身份唯一，文件摘要通过。但它们采于 21:01–21:03，晚于帧时窗口，不能用其 phase 分布冒充之前某个窗口的成员状态。dense 快照确实包含更多正在分配的成员；单独的 phase 位必须结合 assignment 使用。

|---|---:|---:|---:|---:|---:|

这是读池位置的几何成本筛查，不包含实际局部恢复、各阶段真实半径和接触适用性；也没有把旧 256 次预算当作完整性标准。候选膨胀与内存局部性仍有优化空间，但这些计数不能换算 GPU 毫秒，不能证明漏碰撞，也不能推翻已经观测到的连续索引完整链退化。

两条 querysequence 都通过现有校验工具：64 帧、帧标签和代次连续、全部摘要正确，且 65,527 个稳定身份在整段中不变，**现在可以开展每帧／4 帧／8 帧重建的真实运动几何回放**。

- motion：抽样相邻帧位移 p50/p95 约 **0.053 / 0.108 m**，逐帧不动比例中位约 0.041%。
- Dome：相应位移约 **0.068 / 0.138 m**，不动比例中位约 4.18%。
- dt 随帧变化，包含约 0.039–0.043 s 的较长步长。序列采集经过插桩，不计入 FPS，也不能当成静态 refit。

本轮没有运行新的 CUDA/RT 周期性能成绩。数据已具备条件，不需要再把离散快照拼接为运动；后续仍须计入 BVH、描述符、精确复核和互操作，且查询几何通过不等于完整物理或客户端 FPS 通过。

## 后续优先级

1. **补齐低可见慢窗归因**：导出合并绘制父范围、MODEL 阴影准备／绘制及提交量，为 Iris 整段计时补实际身份，核对完整父子范围；再判断阴影、世界绘制或合成哪项占关键路径。
2. **拆分输入准备，单独定位 Dome 导航**：先取得子项成本，再做有针对性的索引／状态优化。MODEL 更新约 2 ms 仍值得优化，但不是当前慢窗的完整解释。
3. **使用这两条真实连续序列评估 CUDA/RT 维护周期**：先做几何成本筛选；有净收益才推进 continuation 与完整物理。
4. **补足三轮受控客户端记录**：保持同一相机、初态和攻击阶段。当前一个进程中的不同场景不能充当独立 A/A；不据这轮 FPS 差异发布优化收益。

若先使用现有包补查阴影，可在低可见慢场景单独执行 `profile on`，关闭聊天保持场景约 10 秒，再执行 `profile details`，最后 `profile off`。完整命令前缀为 `/cmi particle`；结果会进入 debug.log。该粗测与 frames、capture、querysequence 分开进行，关注 `MODEL shadow` 条目；尚不能替代同帧阴影 CSV。

本次仅分析和保存证据，没有修改生产引擎、着色器、数量、频率或光影选项。
