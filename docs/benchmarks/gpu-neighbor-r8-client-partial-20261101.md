# R8 客户端部分数据分析：Complementary 水平地形重负载（2026-11-01）

本轮实机数据支持继续使用生产 OpenGL：有效的 event 和 combined-unsorted 窗口均约下降 13% FPS。此次只做分析，不修改生产代码、实验后端或已交付包。

## 输入与可信范围

冻结 debug.log、7 个窗口的主 CSV/JSON、相机/提交/阶段/硬件 sidecar，以及本会话 18 份选项上下文；共 61 个文件，逐文件 SHA-256 见 manifest.json。分析脚本核对全部原始摘要、主帧 p50/p95/p99 与 JSON 一致性、硬件和提交记录的帧/发布代次关联。

同一客户端进程 PID 33500，RTX 4070 Laptop，驱动 581.15，2560×1506，VSync 关闭、自动降频关闭。七窗均至少 30 秒/1,000 帧，invalid_reason 为空、GPU 缺样为零。Complementary 五窗相机位置/朝向/FOV 逐帧完全相同（pitch 2.400°、FOV 70°），限帧 120；后两窗明确 pack=(off)、限帧 240，二者相机相同（pitch 1.650°），必须独立比较。

光影五窗均为 ComplementaryUnbound_r5.9.3，source=da43d77bf336，实际 402 项 options=2f845d3b8761。原生 DLL=e6dc7735d894…、ABI 8；诊断回执的规范 JSON 哈希 c12f780be0e4… 与本轮交付 JAR 一致。MODEL 输入每窗均为 65,529；普通粒子/可见量和真实 GPU 攻击阶段仍变化，不能伪称严格输入回放。

## 成本归因

| 普通分离：p50 ms | event（光影） | combined-unsorted（光影） | combined（关闭光影） |
|---|---|---|---|
| worker 启动前排队 | 0.012 | 0.012 | 0.011 |
| worker 启动→输入校验完成 | 15.544 | 15.337 | 2.555 |
| 输入校验完成→输出回读完成 | 3.283 | 2.970 | 3.670 |
| 通知→消费 | 0.010 | 0.010 | 0.009 |
| CUDA native-total | 3.208 | 2.898 | 3.604 |
| 渲染线程 handoff 墙钟 | 18.392 | 17.911 | 6.061 |

worker 启动约 12 微秒、通知后消费约 10 微秒，当前证据不支持继续优先抠 JNI 唤醒。输入校验前的 15 ms 包括外部 Fence、等待 GL 输入生产及小封套回读/完成通知；这些细分 GPU 字段在正式 FPS 样本中都是 -1，无法再分解。它也可能反映已有 GL 排队工作，不能把 15 ms 全算作新增后端开销，或仅据此证明 CUDA/地形完全没有重叠。需要单独定位样本的同流事件/完整时间线；不要把详细插桩混入正式 FPS。

生产 CPU submit p50 为 5.34–5.93 ms，实验为 24.24–24.30 ms，接近整帧；该字段是墙钟而非 CPU 利用率。原生任务等待在主线程变得可见。实验 update.model 的 GL GPU 范围约 1.01–1.07 ms 仅覆盖统一程序自身，原生查询、交接和后段另计；不能据此宣称 MODEL 从 2.1 ms 加速到 1 ms。原生产整个 update.model 为 2.098–2.135 ms，当前原生查询 native-total 本身就达 2.898–3.208 ms，尚无可直接替换的完整成本优势。各范围有嵌套/跨流关系，表内中位数禁止求和估算整帧。

排序成本确实存在：event 行排序 p50 0.880 ms，combined-unsorted 为约 0.001 ms（空标记开销，不是仍执行排序）。但分页查询自身约 2.181 ms；event 的 count/write 分别为 0.795/0.900 ms。两窗 NNZ 中位数分别为 1,051,608 与 921,399，输入已不同，不能把 native-total 的 0.31 ms 差额全部归因于分页或无排序。

### Dome 与容量

- event 的 1,213 帧只有普通分离；combined-unsorted 的 1,202 帧有 144 次 Dome 交接（其中 8 次 Q=0），约占 12%。非零阶段查询可达 12,287，Dome NNZ 中位数 321,967，原生 GPU p50 1.872 ms、handoff 3.996 ms。该窗不是同一普通分离负载下的纯排序对照。
- 将 Dome 标记与当前帧 GPU/CPU、下一次 runTick HEAD 间隔关联：无排序组合有 Dome 帧的 GPU p50 26.515 ms、下一间隔 26.396 ms；无 Dome 帧分别 24.647/24.644 ms。这是相关分组，不是独立因果对照；interval_ms 属于两次 HEAD 之间，不能误配为当前阶段耗时。
- 关闭光影的 combined 窗有 1,896/2,656 帧 Dome，Q 中位数 9,332、NNZ 17,513，仍花 native-total 0.739 ms、handoff 2.396 ms；BVH 维护 p50 0.495 ms，高于本次查询本体 0.154 ms。低命中 Dome 的维护/交接比重高。
- 所有保存的实验硬件记录 Java 侧 consumed=true、overflow=0；普通实际 NNZ 约 0.9–1.05 百万，而 CSR capacity 约 4.06 百万，不能把容量当作邻居数。无排序普通页数 p50 77,129，约 10.59 MiB/64 MiB；没有页池溢出证据。ring busy 表示槽位未可复用，与 CSR/页池容量不足不是同一问题。Java consumed 不单独证明 shader 内部接受或完整物理正确，仍需独立语义/画面检查。

### 绘制与光影竞争

生产合并粒子绘制父范围 p50 仅 0.278–0.317 ms；body 可见量 p50 280–314，实验约 267/454，相对 65,529 个模拟 MODEL 很少。当前已记录的粒子绘制范围不支持“粒子绘制是新增 3 ms 主因”的判断。composite/deferred 在各光影窗约 2.32–2.42/1.54–1.60 ms，没有随实验出现同量级增长。未覆盖的地形区间不能用整帧减去阶段中位数补成精确地形成本，RT/SM/带宽各占比仍未知。

## 下一步顺序

1. 先排查真实三槽长时间运行/切换下的 quarantine：记录首次失败状态、槽位、nonce、场景帧/阶段/资源代次、消费与退休 Fence；复现 production→combined→production，自动回退即时明确提示。当前日志只有最终状态，先补故障定位，不能把失败回退窗放进 A/B。
2. 对有效 event/组合路径做独立时间线定位，拆清 GL 输入何时真正可用、外部 Fence、封套 D2H、查询、首个消费者及退休；现有通知尾部已经很小。优先寻找当帧合法输入更早生产与不依赖新粒子的合法工作窗口，保持当帧粒子/阴影契约。
3. 对 Dome 做同 ordinary 策略的固定混合对照：只改 Dome native/完整 GL；覆盖 Q=0、约 1.2 万且高 NNZ 的真实状态。现有 gl-dome(policy16) 与 combined-unsorted(policy15) 同时改变普通查询/通知/排序，不能直接独立归因。Q=0 的查询内已有早退，不要重复声称省掉尚不存在的 BVH 构建；跨 API 固定开销仍需核对。
4. 分页/无排序保持独立、匹配实际原点/半径/阶段/NNZ 后重测。当前分页内核并不便宜，先证实完整链净收益，再考虑组合；不要因无排序省下约 0.88 ms 就预期 FPS 上升。每 4/8 帧 refit 既有退化证据继续保留，不据此开放未经验证的客户端周期。

已有窗口足以拒绝当前版本替换生产，不必先为全部十个慢后端补齐长测。后续实现修复和针对性定位后，再以固定初态重做生产 A/A、候选 A/A 和交错 A/B，三轮独立进程；每窗 ≥30 秒且 ≥1,000 帧。正式准入仍须完整帧改善超过匹配噪声、1% 和 0.1 ms，p95/p99 无稳定退化。此次只有一个进程，不能宣布正式验收通过，也不能宣布专用硬件在所有未来实现中必然无效。
