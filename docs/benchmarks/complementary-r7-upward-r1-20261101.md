# Complementary R7 竖直向上：首组客户端帧时分析

日期：2026-11-01。此次仅分析和冻结记录，没有修改生产代码或实验实现。

## 结论

**这两个窗口中，rt-aabb 的完整客户端表现明显更慢，没有观察到专用硬件卸载带来的 FPS 收益。** 平均 FPS 55.05→40.67，下降 26.11%；帧时 p50 增加 6.2868 ms，p95/p99 也增加。原生任务均正常消费，未发生溢出或参考回退，MODEL 输入维持 65,528，未重现容量清零故障。

这是同进程各一个窗口的描述性结果，不是正式受控 A/B，也不能据此宣布 RT Core 在所有场景无效。两窗相机 yaw、攻击构成和装饰总量不完全匹配；没有两侧 A/A 和三轮独立进程。竖直向上是轻地形、高 MODEL 可见量场景，不能代替水平重地形竞争验证。

## 1. 窗口与完整帧时

- production：`frames-0e57fa2d-d5e2-49a0-b82e-036771745006`，北京时间 12:05:37 起，30.0095 秒、1,652 帧。
- rt-aabb：`frames-e06604f0-e48e-4df7-b7b3-11e9dbce7868`，12:09:02 起，30.0187 秒、1,221 帧。
- 两窗 `invalid_reason` 均为空，GPU 样本无跳过；均超过 30 秒和 1,000 帧。完整捕获和连续输入采集都已在 FPS 窗口前结束。

| 指标 | production | rt-aabb | 观察到的变化 |
|---|---:|---:|---:|
| 平均 FPS | 55.049 | 40.675 | −26.11% |
| 主帧间隔 p50 | 18.2874 ms | 24.5742 ms | +6.2868 ms / +34.38% |
| 主帧间隔 p95 | 18.8273 ms | 27.2394 ms | +8.4121 ms / +44.68% |
| 主帧间隔 p99 | 19.0047 ms | 28.1518 ms | +9.1471 ms / +48.13% |
| 主帧 GPU p50 | 18.1228 ms | 24.5033 ms | +6.3805 ms |
| CPU 提交墙钟 p50 | 5.0565 ms | 24.1317 ms | +19.0752 ms |

GPU 范围为 runTick 开始至交换前，主帧间隔还包括交换和限帧。CPU 提交墙钟包含阻塞等待，不能解释成 CPU 计算量或利用率增加了相同比例。两侧限帧均为 120、VSync 关闭，实际帧率远低于上限。

初始化耗时 756.7 ms，发生在 rt 窗口开始前约 22 秒，不包含在该窗口中。rt 的六个约 5 秒分箱 p50 为 26.143、26.031、24.321、24.778、23.308、22.770 ms；生产为 18.388、18.356、18.311、18.315、18.118、18.181 ms。退化不是只由首帧初始化尖峰造成，但 rt 窗口也并非完全稳态。

## 2. 匹配程度与已确认的运行状态

相同项：RTX 4070 Laptop / 581.15、2560×1506、主世界、ComplementaryUnbound r5.9.3、全部 402 项实际选项、宏、附件格式和深度上下文；两个 profile 上下文 JSON 逐项相同。引擎摘要和诊断回执相同，回执 `4d9e2be8…` 与容量修复版分发一致，自动节流均关闭。

| 场景项 | production | rt-aabb |
|---|---:|---:|
| MODEL 输入 p50 | 65,528 | 65,528 |
| 总存活数 p50 | 145,911 | 145,591 |
| 身体可见数 p50 | 64,527 | 64,284 |
| Dome 合同出现帧比例 | 66.77% | 33.91% |
| 螺旋合同出现帧比例 | 0% | 68.71% |
| 相机 pitch | −90° | −90° |
| 相机 yaw | −543.30194° | −541.65192° |

两窗内部相机均固定，位置与 FOV 完全相同；窗口之间 yaw 相差 1.65002°。即使 pitch 为 −90°，yaw 仍改变画面绕视线的旋转，不能当作严格相同视图。总存活数中位数差 −0.2193%，超过既定 0.1% 的数量匹配阈值；MODEL 数相同，差异主要在装饰。合同是 CPU 包阶段，不能据此推断每个 GPU 成员的实际阶段。

因此单窗质量检查通过，正式 A/B 匹配门槛不通过。不同攻击分布、轨迹、dt 和可见量使得“6.29 ms 全部由某个算法造成”的精确因果说法不成立。身体和透明层的可见计数对应相同 MODEL，不能相加当作模型数量。

同代计数、攻击代次和阴影代次在两个窗口中全部对应；rt 的 1,221 个普通分离任务和 414 个 Dome 任务均为 `current native result`、`consumed=true`、`overflow=0`。普通任务约 65,528 点/查询，Dome 为 65,528 点、24 查询。CSR 容量约 406 万是容量上限，不是实际邻接条目数，不能用它计算平均真实邻居数量。

## 3. 成本定位

以下为各自记录范围的 GPU p50，父子区间可能嵌套，**不得相加中位数作为完整链或整帧时间**。

| 范围 | production | rt-aabb | 解释 |
|---|---:|---:|---|
| `update.model` | 2.0644 ms | 1.0035 ms | 实验仅记录前段/提交，继续计算已移出此范围，不能宣称 MODEL 快了一半 |
| 合并绘制父范围 | 4.8138 ms | 5.0002 ms | 没有出现绘制卸载收益 |
| MODEL 身体 | 2.9768 ms | 3.1939 ms | 不能仅归因于硬件竞争，攻击/轨迹也不同 |
| MODEL 透明层 | 1.7265 ms | 1.7428 ms | 与身体同属合并绘制父范围 |
| 输入准备 | 0.6175 ms | 0.6195 ms | 典型值基本一致，尾部也接近 |
| Dome 接触（活跃帧） | 0.1208 ms | 2.1811 ms | 原生维护与交接进入接触链，且两侧不是相同输入 |

生产 `scene.compute` 为完整范围，p50 3.6516 ms；实验则拆成 prefix 1.8053 ms 和 continuation 2.1309 ms，原生 CUDA 区间另计。三者的时间源、范围和依赖不同，不能直接拼成一个“完整计算 p50”与生产比较。完整客户端 GPU 24.5033 ms 和主帧间隔才是当前可靠的总成本观测。

### 普通分离：查询本身与交接都不便宜

rt-aabb 原生 GPU 区间 p50 为 4.6910 ms，其中单独记录的计数查询为 1.5841 ms、写入查询 1.7407 ms、BVH 维护 0.5683 ms、描述符 0.0295 ms、扫描 0.0205 ms。原生总范围还包含排序、封装/其他未单列成本，不能把分项中位数之和当作总中位数。

源码的 RT AABB count/write 两遍都会执行遍历和自定义 intersection，精确距离复核在普通计算单元上完成；不应把这两段全部解释成 RT Core 时间。当前原生 GPU 区间本身已经大于生产 MODEL 的约 2.06 ms，尚未加上前段/继续和交接。

更明显的是：普通分离的主线程交接范围 p50 为 **17.0514 ms**，worker 墙钟为 **16.7107 ms**。按同一帧逐对计算，worker 墙钟减去原生 CUDA event 区间的差值 p50 为 **12.8263 ms**。这是“不在该 CUDA event 区间中的墙钟部分”，包含 GL 生产者就绪、外部 Fence/调度、输入及输出 64 字节回读和主机通知等，不能全部叫作纯互操作损耗或纯 CPU 计算。

源码已经在 GL signal 后调用 `glFlush()`，不能凭现象归咎于漏 flush。现有记录没有完整跨 API 时间线，仍需把这些等待边界拆开，才能确定主因。当前日志的“前阴影提交”只说明提交位置，没有证明实际 GPU 重叠成功。

### Dome：低查询量仍支付整池维护

414 个活跃任务每次只有 24 个查询，却对约 6.55 万候选维护 BVH。原生 GPU 总区间 p50 0.6978 ms，维护 0.5263 ms；按同任务逐对算，维护占比中位数约 75.46%。交接墙钟 p50 3.8908 ms，worker 2.8908 ms。

rt 窗口内，有 Dome 原生任务的帧 GPU p50 为 26.1366 ms，没有的帧为 23.6472 ms；这也是分组观察，不是同输入受控差值。不能把生产 0.1208 ms 的旧查询直接当成新语义完整 GL 查询的性能。

## 4. 新回放输入是否可用

完整捕获 `R7_comp_horizontal_full-ee9bd778-7a19-42da-92c8-a258a7b35cb4` 的 schema 3、资源/载荷 SHA、命令边界和发布代次验证通过：97 条命令、45 个资源、19 个程序，冻结资源 440.90 MiB，发布/粒子群/风暴代次均为 4487。它现在具备完整命令链范围，不再只是历史更新入口快照。

此次未运行 GPU 二进制回放，不能把结构/哈希通过称为实际重放输出通过。新捕获的 GL 版本为 4.6，而现有 `R7ChainReplayGpu` 入口请求 4.5，严格二进制回放前应对齐上下文。文件名中的 horizontal 不能用来证明捕获相机等于本次向上 FPS 窗口；完整捕获未声明相机姿态，且取得时间更早。

两条新序列均为 schema 3、64 帧完整连续，读取池和 Dome 阶段身份集合稳定，没有缺帧或校验失败，具备后续重建/4帧/8帧 refit 对照所需的拓扑条件：

- motion：每帧 65,528 个普通实际查询，半径 **1.0–1.4**；无 Dome 阶段。不能继续固定所有半径为 1。
- dome：普通查询 54,600–54,612；Dome solve/apply 实际查询 **10,933–11,778**，solve/apply 半径范围约 **0.78–2.308**，含正确 post-MODEL 位置。

Dome 序列与 rt FPS 窗口的 24 查询是不同负载，不能混用成绩。连续输入中的 dt 也会变化，例如 motion 为 0.008–0.114 秒、Dome 为 0.010–0.041 秒，必须按逐帧实际原点、半径和位置阶段回放；不能换成固定 1/60 秒后仍声称匹配真实输入。捕获与 FPS 成绩继续分开。

## 5. 下一步优先级

1. **先拆分交接等待。** 在离屏真实输入回放中标出 GL signal 就绪、CUDA wait 结束、输入回读、查询、输出回读、通知与 GL 消费；比较串行/合法提前提交。保留当前帧依赖、代次校验和完整回退，不以旧帧结果换等待。
2. **再看 count/write 重复遍历与结果消费。** 对相同真实输入比较 RT AABB、triangle 和 CUDA 对照，单列 CSR 行排序与封装；不能只盯约 0.57 ms 的 BVH 维护。若改变归约顺序，重新按既有数值误差与物理规则验收。
3. **将低 Q 的 Dome 单独决策。** 比较同语义完整 GL 与原生路径的全部维护/交接成本，不强制每个只有 24 查询的阶段都卸载整池。普通与 Dome 位置阶段不同，不能无条件复用索引。
4. **利用两条新序列验证重建周期。** 现在可以比较每帧、4帧、8帧周期，但已有 refit 失败证据保留；仅测前 128 查询的结果不能当成全量 6.55 万查询成绩。
5. **优化后再扩大客户端采集。** 当前不急于扩成八包长测。先固定 yaw、场景初态和攻击安排，取得生产/候选两侧 A/A 与交错 A/B；重点再覆盖水平重地形。最终仍需三轮独立进程的整帧门槛。
