# 悦灵风暴美术效果：统一开发顺序

状态：🟡 开发顺序与实施记录。日期：2026-10-27。顺序1～2、八包体积雾原生路径，以及八包原生裂口与共享天空视觉均已由用户验收；多人／大型载具的其他验收仍见[本批实施状态](allay-storm-rift-implementation-status.md)。序号7代码已接入，自动验证与用户实机验收分开记录，最新要求见[分形巨眼方案](allay-storm-stage7-eye-art-plan.md)。

实施更新（2026-10-26）：保留现有风暴、悦灵维度及八包实体合并／阴影／探针／地平线修复验收，并记录本轮用户确认的八包原生雾验收。新增入口已连接真实服务端协调器、Create／Sable／Aeronautics桥接和持久化恢复；代码／GPU／隔离服务端测试与客户端验收分别记录。版本继续只作验证样本标签。光影集成状态见[光影集成说明](shaderpack-integration.md)。

本文合并[天穹灵潮美术方案](allay-storm-art-direction-plan.md)与[天幕裂口／维度入口方案](allay-storm-sky-rift-plan.md)。两份方案原有P／R批次保留为功能分组；实际推进优先按本文的统一序号执行。

## 1. 排序结论

推荐主线：**基线与状态 → 光影接入探针 → 高空订阅 → 共用天空 → 裂口与传送 → 宏观构图 → 小规模装饰与真实事件 → 三招 → 后处理与体积 → 百万扩量 → 原生增强与八包验证 → 综合验收。**

排序依据有三条：先解决会让效果消失／传错维度的前置条件；先让低密度画面成立；高成本与包专用效果建立在可测的公共路径上。每个步骤都应有可单独检查的结果，不以“整场风暴一起完成”作为唯一验收单位。

需要调整原方案的部分：

- 远景摘要从原先P2a的后续扩展，提升为裂口与高空演出的前置依赖。现有三维196／260格追踪不足以持续覆盖入口附近。
- 共用天空的接口和简易实现提前，未来天空的最终美术可以后定。裂口不能长期依赖一套与维度本体无关的专用贴图。
- Iris完整适配仍靠后，但最小可行性探针提前，避免全部效果完成后才发现目标program／buffer无法按预期接入。
- 性能计时和生命周期从第一批开始；百万扩量阶段负责验证容量、覆盖率与降档，不承担“第一次发现所有性能问题”的职责。
- 传送属于玩法配套，应先形成独立服务端闭环，再与裂口一起对玩家开放。不能在尚无入口提示时默认启用高空自动传送。

## 2. 逐项顺序、前置与交付

以下序号是推荐开发顺序，不是每帧GPU绘制顺序。未实施的新增名称仍为提案。本轮序号7采用c=-0.5的完整标准二次Julia天空投影，与眼点y=64正下方所见的真实风暴组成巨眼；保留中央表面与自然厚度，不挖成眼眶，仅用统一缩放和刚性放置校准。已提供[离线数值渲染](allay-storm-julia-offline-renders.md)，尚未进行游戏透视合成。仅使用有效光影包云，无包／无云／关云不补云。悦灵天空恢复主世界同一套原生天空，太阳相位落后12000 tick，天气沿用主世界一致的既有行为，不再新增专属天空色调。

## 3. 各阶段的发布边界

### 第一批：入口功能样机，步骤0～6

交付的是低复杂度、功能完整的版本：达到16,384后高空可见裂口、内外天空替换正确、能够进入安全落点。共用天空可以仍是临时profile，但必须同时用于本体和预览；对外应明确它尚非最终悦灵天空美术。

服务端规则测试可在第3步就开始，目标加载／安全落点服务也可独立开发；第6步才把它与可见裂口接通。不能为了等待美术延后规则正确性验证，也不能把不可见的自动传送提前作为默认玩法放出。

### 第二批：标准画质美术完整，步骤7～14

按本轮修订，交付分形巨眼、原生云衔接、稀疏星海、三招、裂口撕裂边缘、可控Bloom与基础空气层次，低密度下已经成立；取消自制六臂云冠。装饰上限可逐渐达到标准档262,144，但不以百万粒子作为这批的完成条件。

第2步确定的是共用发光／透射／深度接口，第14步才提高体积质量。因此后加体积不应要求推翻第8～12步的粒子和尾迹数据。早期样机可先使用单位透射纹理作为占位。

### 第三批：华丽档与原生增强，步骤15～18

交付百万装饰候选、可验证的自动降档及原生增强；八款样本均检查基础显示，增强按能力分别验证。光影适配的计时需要重新覆盖实际包中的新路径，因为它们改变了曝光、Bloom、云与合成开销；不能沿用第15步无光影结果直接声称支持相同预算。

第18步允许并行准备资产候选，但最终取舍在八包效果矩阵验证后完成。此处“并行”指工作依赖允许，不要求多个开发进程或agent同时改同一文件。

### 第四批：综合验收，步骤19

只有完整客户端、多玩家与所有主要效果组合通过，才能将指定配置标为已支持。每一步的专项检查持续执行，最终验收不会替代它们。没有实现变更的设计轮不需要运行构建或GPU测试。

## 5. 验证节奏与成本判断

开发工时不按粒子数量线性分配。步骤2、5、6、9、12、14、17是主要技术风险点：它们分别涉及包专用管线、正确天空遮挡、目标世界准备、GPU状态事件、复杂招式状态、透明／体积层次和Photon环境天空。应先做最小案例，案例成立后再添加外观细节。

步骤7、10、11、13、18通常更容易产生可见进展，但仍应在其共享依赖具备后推进。例如先用薄云冠和少量星尘确定形状，可以尽早验证美术方向；先精修百万粒子的每张贴图则不能回答宏观构图是否成立。

每项至少记录：基线／改后截图或短录屏、适用机位与渲染模式、该项GPU区间、整帧变化、额外资源及未覆盖场景。仅涉及可逆材质参数的细调以截图／实机检查为主；涉及成员事件、传送、GPU提交与资源生命周期的变更应有对应逻辑／真实GPU回归。

实施时不要以当前设计里的≤3ms／≤5ms目标当成既有性能事实。先确定目标机器、分辨率、真实成员数量与光影设置，再决定默认档；初期推荐标准档，百万实例作为华丽档明确能力。

当前**步骤3～6代码闭环已接通，自动入口已启用**，真实服务端已验证多人嵌套乘骑、Create座位、Sable连接结构与故障恢复；八包原生裂口和共享天空视觉本轮由用户确认通过。多人／大型载具其他验收继续单列，不将自动验证记成整批实机通过。序号7本轮仅提交[分形巨眼美术方案](allay-storm-stage7-eye-art-plan.md)，不修改已经运行的渲染、时间或传送代码；新方案实施后需重新验收。
