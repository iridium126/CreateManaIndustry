# HexJIT 修复与性能记录（2026-10-06）

审查基线与问题详情见 [实现审查](hexjit-implementation-review-2026-10-06.md)。六项问题已按报告顺序修复；性能目标按本次用户确认完成。性能数据只作为测量记录，测试中没有 25 ms 上限断言。

## 六项修复

| 问题 | 修复 | 回归结果 |
|---|---|---|
| 跳过有行为的玩家回调 | 区分真正空回调与只读回调；保留事故消息、半径更新、图案记录和声音预算 | 缺参事故消息 OFF/AUTO 均为 1 次 |
| 覆写的操作上限被忽略 | 每步使用实际虚方法返回值；只有基类原样返回值或显式纯常量契约才能缓存 | 上限为 3 时均执行 2 次 Tick，ops 均为 3 |
| 直接 Tick 的异常逸出 | 在直接执行边界恢复 Exception → MishapInternalException，不重放操作 | 预检查异常均返回 ERRORED |
| 未验证初始栈的子栈跳过 | 只有确实验证成功且 Iota 度量稳定的输入才产生子栈证明 | 超限输出均拒绝；原版允许的缩小操作仍成功 |
| 修改不可变 image / 状态别名 | 删除 CastingImage 可变字段 Mixin；自定义环境复用 Tick 状态需显式契约 | 保存的历史 ops 为 `[1, 2, 3, 4]`，对象不再别名 |
| 被淘汰的编译产品仍被持有 | 共享 pending 引用计数；最后引用释放时取消任务；预算覆盖待发布产品 | 不同描述淘汰、共享任务存活、关闭竞争测试通过 |

`CompilationCache.Stats` 增加待编译描述数和待发布字节数。异步任务结束后不得在已关闭缓存中重新占用预算。

## 性能实现

- 连续 Tick 使用索引循环，退出或事故发生时恢复准确的剩余 continuation；成本、实际操作上限和世界副作用仍按顺序处理。
- 相邻 Tick 只在个人媒体池已证明足够且虚拟余额有效时复用预检查；余额不足、环境不符合条件或禁用相关开关时走原路径。
- 已验证的标准 Staff 回调保留其效果，省去中间结果包装；自定义回调、观察者及不兼容的 Mixin 走通用路径。
- 缓存相同不可变括号引用列表；连续向量引用保持括号、逃逸、模拟和操作上限语义。
- 属性实例干净且缓存半径仍与属性值一致、没有观察者、中间没有效果的纯引用段，可合并重复计算。启用法杖声音合并后，相同声音首次播放后即可折叠，不必等到 100 次声音预算耗尽。返回的 CastingImage 保持不可变。
- 半径属性缓存实例定位，每次需要刷新时读取最新值；属性表新增实例会使定位失效，不会为了优化而创建玩家属性实例。
- 统计标识查找可缓存，实际统计写入与事件仍逐次执行。
- 普通 pattern 查找缓存现在默认启用，仍按注册表 epoch 失效。动态 special handler 的匹配仍逐次调用。

新增的 `TickStateReuseEnvironment` 是自定义环境的明确状态复用契约；`StableMaxOpCountEnvironment` 要求完整上限查询为无副作用且在单次排队施法内恒定。未知环境无需实现这些接口，继续使用保守路径。

## 单次施法法杖声音合并

服务端配置 `[hexcasting.jit] coalesceStaffSounds = true` 默认开启。同一个开关同时控制法杖声音合并及其随机数流变化。设置为 `false` 后保留原来的法杖声音播放次数和随机种子消耗。

仅拦截 `StaffCastEnv.postExecution` 中的法杖播放调用，以及已验证的 Staff 快速回调。不拦截普通 `Level.playSound` / `ServerLevel.playSeededSound`。同参数法杖声音已经播放过时，在调用平台声音函数之前跳过重复项，省去随机种子生成、事件对象、声音包和广播；相邻重复项的比较也不创建新的合并键。

合并键覆盖世界、排除的玩家、声音、声源、精确位置、音量和音调，浮点参数按原始位比较。缓存只记录成功返回的平台播放调用，施法结束时清理，嵌套施法独立。

存在 NeoForge 位置声音监听器、非标准世界实现或平台声音方法被其他变换修改时，保留逐次声音播放及 RNG 消耗。监听器检查使用包含继承监听器的实时列表，动态注册也会触发回退。平台验证 Mixin 只检查字节码，不向普通声音函数注入拦截代码。

法杖原有的 100 次播放预算仍按原来的尝试次数推进，即使中间纯引用回调被折叠也补齐计数，避免后续不同声音获得额外预算。声音 RNG 使用 `Level.threadSafeRandom`；法术及 Tick 自身的世界 RNG 不因这一开关而被跳过。

验证包含：

- 相同参数只进入平台播放函数一次，300 次引用的原版声音预算仍为 100，最终 image 保持 OFF/AUTO 一致；
- 开启时两次相同法杖声音消耗一次种子，关闭时消耗两次；普通声音始终消耗两次；
- 位置不同及跨施法的请求分别播放，非相邻重复项仍能合并；
- 动态注册声音事件监听器后保持事件次数与参数修改；
- 脏属性及已被其他代码重新计算、但环境半径仍过时的属性均阻止折叠；刷新后可重新折叠；
- 存在 PostExecution 观察者时保留全部中间回调。

## 测量

工作负载为原有 Tick 参考法术：92,160 次 Tick、99,510 ops。保留原来的状态差分与世界 RNG 检查，额外记录 20 次预热后的 9 个墙钟时间样本。

| 阶段 | 中位耗时 |
|---|---:|
| 六项修复后的首轮 | 36.25 ms |
| 引用循环折叠 | 27.19 ms |
| 属性实例定位优化 | 24.01 ms |
| 首次完整验证，含声音广播合并 | 21.29 ms |
| 最终完整验证，仅法杖声音合并并跳过重复种子 | 24.16 ms |

最终样本为 `25.6464, 23.1149, 22.7937, 22.8229, 28.1018, 23.8062, 25.1431, 25.8866, 24.1637 ms`。同机其他任务会造成波动，轮次间变化不能单独证明某项优化的收益。参考测试使用 FakePlayer，不能直接当作所有玩家、模组组合和法术的耗时。

本轮原版状态、世界变化、RNG、施法回调和最终 image 的差分检查仍保留。耗时没有测试断言。

## 声音合并的独立性能分析

只切换 `hexJitCoalesceStaffSounds`，其余优化配置保持一致；31 组 AUTO 对照交替先开后关、先关后开，保留法术状态差分断言，计时关闭指标收集。另运行指标采样确认路径，日志为 `build/hexjit-sound-performance-ablation.log`（3 项服务端测试通过）。

| 指标 | 开启 | 关闭 |
|---|---:|---:|
| 整次施法耗时中位数 | 20.9872 ms | 21.223599 ms |
| 进入平台的法杖声音调用 | 2 | 100 |
| 跳过的重复声音请求 | 98 | 0 |
| 纯引用段折叠次数 | 180 | 180 |

两个耗时中位数相差约 0.2364 ms（1.11%）；但逐对计算“关闭耗时 − 开启耗时”的中位数仅为 0.0144 ms，31 对中开启更快 17 对、更慢 14 对。样本约在 20–33 ms 之间波动，因此本次数据不足以证明稳定的整体耗时改善，更不能把此前所有 Tick 加速归因于声音合并。

收益来源确实存在：98 个重复请求省去了声音种子生成、声音事件对象、声音包和广播；相邻重复比较不再分配键；满足纯度条件的引用段能更早省去中间 image、回调及上限查询。不过，Staff 原本每次施法最多尝试播放 100 次声音，且关闭合并后预算耗尽仍可折叠纯引用段。因此，这个开关对 92,160 次 Tick 的工作负载只影响有限的前缀，不会省去 Tick 的世界效果、媒体处理和一般 VM 运算。

当前 GameTest 使用 FakePlayer，没有真实客户端连接，无法衡量网络发送及客户端播放成本。真实服务端的广播还会遍历在线玩家并向范围内玩家发送声音包，玩家多或大量重复施法时，减少这部分工作可能更有价值；具体收益仍需在对应环境测量。

保留该功能适合作为减少重复声音及少量 CPU/分配工作的优化；当前证据不支持把它视为参考 Tick 的主要性能优化。

```powershell
.\gradlew.bat -I scripts/hexjit/gametest.init.gradle -PhexjitSoundAblationSamples=31 runGameTestServer --offline --console=plain
```

对照只记录耗时，不断言固定上限或要求开启必须比关闭更快。
